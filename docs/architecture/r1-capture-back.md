# Plan technique backend — R1 capture (r1-capturer-1 #27, r1-capturer-2 #28)

tech-lead-back, 2026-10-22. Cadre : ADR 0002, 0003, 0006 (amendé ce jour), 0008, 0009, 0015. Contrat : `docs/api/openapi.yaml` (tag `capture`, à relire par tech-lead-front). Code dans `fr.zonumental.capture` uniquement, plus deux classes publiques ci-dessous.

**Données — `V8__capture.sql` (#27).** Schéma `capture`, table `capture.capture` : `utilisateur_id uuid`, `numero_monument int`, `capturee_le timestamptz default now()` (horloge serveur, RG-048), `distance_m double precision`, `photo_id uuid unique`, PK/`UNIQUE (utilisateur_id, numero_monument)` (RG-034, concurrence). Aucune FK inter-schémas (ADR 0008), aucune colonne de position/précision/appareil (RG-049). Même migration : table `event_publication` du registre Spring Modulith (copier le `schema-postgresql.sql` de la version du BOM), dépendance `spring-modulith-starter-jdbc`, `completion-mode=delete`, `republish-outstanding-events-on-restart=true`.

**API publiques des autres modules (classes `public` à la racine du module).** `compte.Comptes#emailVerifie(UUID)` ; `catalogue.Cibles#pour(numero, lat, lon)` → `Optional<Cible(rayonMetres, distanceMetres, histoire)>`, distance calculée en SQL : `ST_Distance(position, ST_SetSRID(ST_MakePoint(lon, lat), 4326)::geography)` (géodésique exacte, colonne `geography` déjà là, V3). Monument retiré = ligne absente = `introuvable` (R1-70).

**Endpoints.** `POST /api/captures` (multipart : `numero`, `latitude`, `longitude`, `precisionMetres`, `photo`) → 201 `Capture` + `histoire`. `GET /api/captures/{numero}/photo` → `image/jpeg` de **l'appelant** (la clé dépend du jeton, aucune adresse vers la photo d'un autre : 404 `introuvable`, 401 sans jeton), `Cache-Control: private, no-store`.

**Ordre des contrôles (RG-053), dans le service `Capturer`, une erreur et un seul `throw ErreurMetier` par étape :** 1 connexion (Spring Security, 401) · 2 `email-non-verifie` 403 · 3 `introuvable` 404 · 4 `deja-capture` 409 (r1-capturer-4 le transformera en remplacement) · 5 `image-invalide` 422 (taille puis décodage, composant `Photos`) · 6 emplacement réservé fréquence/vitesse (r1-capturer-3) · 7 `precision-insuffisante` 422 si `> 100` · 8 `trop-loin` 422 si distance exacte `> rayon`, champ `distanceMetres = ceil(d/10)*10` (RG-046). Le contrôleur ne fait que lier la requête ; validation de forme (`validation` 400) avant l'étape 2, sans renvoyer les valeurs de coordonnées.

**Photo (`Photos`, #27).** Taille : `photo.getSize() > 5 000 000` octets → refus (5,1 Mo refusé quelle que soit l'unité). `spring.servlet.multipart.max-file-size=10MB` pour que l'ordre RG-053 tienne (au-delà, le conteneur refuse : `MaxUploadSizeExceededException` → `image-invalide` dans `ErreursApi`). Format détecté sur les octets (`ImageIO.getImageReaders(ImageInputStream)`), jamais sur le nom ni le `Content-Type` ; seuls jpeg/png/webp. Anti-bombe : lire largeur × hauteur avant décodage, refus au-delà de 24 Mpx. Bibliothèques Java pures : **TwelveMonkeys `imageio-webp`** (lecture WebP, BSD) et **`metadata-extractor`** (tag EXIF Orientation, Apache 2). Pipeline : orientation appliquée (`AffineTransform`) → réduction à 1600 px côté long (`Graphics2D`, bicubique, jamais d'agrandissement) → **JPEG qualité 0,85** via l'encodeur du JDK (nouvelle image = aucune métadonnée). Pas d'encodeur WebP Java sans natif : format unique JPEG (amendement ADR 0006).

**Stockage (`StockagePhotos`, #27).** AWS SDK v2 `software.amazon.awssdk:s3` (+ `url-connection-client`), `endpointOverride` + `forcePathStyle`, propriétés `zonumental.s3.*` ← `ZONUMENTAL_S3_*` (`.env.example`). Clé `captures/<utilisateurId>/<photoId>.jpg`, `photoId` = UUID neuf à chaque envoi. `PutObject` avec `Content-Length` connu : atomique, une coupure n'écrit rien (R1-28). Pas d'URL présignée ni publique : lecture en flux par le backend (ADR 0006). Le front lit la photo avec `fetch` + `Authorization: Bearer` (jeton en mémoire, ADR 0015), puis `URL.createObjectURL` (CSP `img-src blob:` déjà autorisé), révoqué à la sortie de l'écran.

**Enregistrement (#28).** Contrôles 1-8 (lectures seules) → réencodage → `PutObject` → `INSERT … RETURNING capturee_le` en transaction. Violation d'unicité (double envoi simultané) → 409 `deja-capture` et `DeleteObject` de la photo orpheline ; tout autre échec après le PUT → `DeleteObject` puis erreur. Orphelin résiduel (crash entre les deux) : sans lien, effacé avec le préfixe du compte. Refus journalisés en INFO (code, UUID, jamais de position), rétention 30 jours = celle des journaux (Q-27) ; DTO avec `toString()` sans coordonnées (ADR 0008).

**Effacement (#27).** `capture` écoute `CompteSupprime` (`@ApplicationModuleListener`) : `DELETE` des lignes, puis `ListObjectsV2` + `DeleteObjects` par pages sur `captures/<utilisateurId>/`. Idempotent ; un échec laisse la publication ouverte, rejouée au redémarrage.

**MinIO local et tests (#27).** `testcontainers-minio`, conteneur déclaré dans `TestcontainersConfiguration` (donc aussi dans `LancementLocal`), propriétés via `DynamicPropertyRegistrar` comme Mailpit, bucket créé par la config de test (en prod il est provisionné par r0-socle-5, l'appli ne crée jamais de bucket). Tag d'image **figé** : MinIO (AGPL, usage local seulement) ne publie plus d'images communautaires depuis fin 2025 ; dev-backend fige le dernier tag disponible et le note dans `TestcontainersConfiguration`.

**Découpage.** #27 : V8 + registre, `Photos`, `StockagePhotos`, MinIO, écouteur `CompteSupprime`, `GET …/photo`, codes `image-invalide`/`introuvable` (tests sur fichiers piégés : PDF renommé `.jpg`, PNG 30 000 × 30 000 px, JPEG portrait EXIF 6 avec GPS). #28 : `Comptes`, `Cibles`, `Capturer` + `POST /api/captures`, ordre RG-053 (un test par paire d'erreurs simultanées), concurrence (deux envois parallèles), compensation S3.

**Hors périmètre, à signaler.** Export des photos (ADR 0008, interface de contribution `compte` ← `capture`) : aucune story R1 ne le porte. r1-capturer-3 aura peut-être besoin d'une table de tentatives (« un refus de précision ne compte pas »).
